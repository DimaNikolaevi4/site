Не выполнять как часть текущей задачи:

- перенос всего контента в новую структуру каталогов;

- введение `REMOTE_ASSETS` как «исправления» локальной разработки;
- срочный распил `.eleventy.js` на отдельные модули;
- изменение уже работающей модели внешних медиа-ассетов без отдельного решения.

> Эти идеи можно вернуть в отдельный архитектурный этап после прохождения проверок.

## 4. GitHub Actions: build → checks

Workflow должен сначала установить зависимости и собрать V2, а затем проверять результат. Проверки, которым нужен сгенерированный output, нельзя запускать до сборки.

- [ ] Создать `.github/workflows/site-v2.yml`
- [ ] Запускать workflow на push в `site-v2` и на pull request с этой веткой
- [ ] Зафиксировать используемую версию Node по правилам проекта
- [ ] Настроить порядок шагов:

```
checkout → setup Node → npm ci → npm run build:v2 → checks
```

- [ ] Добавить проверки:
  - [ ] `npm run check:frontmatter`
  - [ ] `npm run check:v2:source-boundary`
  - [ ] `npm run check:urls:unique`
  - [ ] `npm run check:urls:generated`
  - [ ] `npm run check:links:v2`
  - [ ] `npm run check:route-shape:v2`
- [ ] Выполнить первый запуск workflow
- [ ] Исправить только подтверждённые ошибки и повторить запуск
- [ ] Зафиксировать итоговый порядок команд в `SITE_V2_CHECKLIST.md`

**Критерий выхода:** первый CI-прогон для ветки `site-v2` зелёный, а ошибка любой проверки делает workflow красным.
